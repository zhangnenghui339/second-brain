# ATS 实测执行方案与步骤（Day 1–14 技术门）

> **本文档回答四个问题：去哪个网站、用什么简历、怎么提交和记录、付费页面什么时候做。**
> 对应第一道 Kill Criteria：**14 天内完成 2 个 ATS × 3 种格式 × 3 次重复，一致率 ≥90%**，否则"中立验证层"（裁判定位）整体回退。

---

## Phase 0 · 准备（Day 1，约 3 小时，高能窗口）

### 0.1 制作测试母本简历

**不要用任何真人的简历。** 创建一个虚构但完全逼真的人物：

```
姓名:     Alex Chen
邮箱:     alex.chen.swtest@<你的域名>.com   ← 用自己域名的邮箱别名，方便追踪
电话:     +1 (415) 555-0142                ← 555 号段为虚构保留段
地点:     San Francisco, CA
目标岗位: Software Engineer（选 SWE 是因为你能人工校验内容质量）
内容:     2 段工作经历（各 3-4 条 bullet）+ 1 段教育 + 8-10 项技能
篇幅:     1 页
```

内容写好后**冻结，此后一个字不改**——所有变体只动格式。这是受控变量测试的根基。

### 0.2 制作首批 6 个变体（V01–V06）

| ID | 唯一改动的变量 | 制作要点 |
|----|--------------|---------|
| **V01** | 无（基线/对照组） | 单栏、Arial 11pt、纯文字、无表格无图标、联系方式在正文首行 |
| **V02** | 工作经历改用**表格**排版 | 其余与 V01 逐字逐格式相同 |
| **V03** | 技能列表改用**图标/符号**（如 ● Python ▸ SQL） | 其余同 V01 |
| **V04** | 改为**双栏布局**（左窄右宽） | 其余同 V01 |
| **V05** | 全文换**非常规字体**（如 Montserrat / Garamond） | 其余同 V01 |
| **V06** | 联系方式移入**页眉**，页脚加页码 | 其余同 V01 |

**制作纪律：**

- 每个变体导出 PDF；工具用 Word 或 Google Docs 均可，但**同一批变体用同一工具导出**（导出器本身是隐藏变量）
- 上传时统一文件名 `Alex-Chen-Resume.pdf`（文件名也是变量，锁死它）
- 本地按 `V01_baseline.pdf`、`V03_icons.pdf` 归档，上传前重命名

### 0.3 建记录表（先用表格，跑通后进 D1）

每次上传 = 一行记录，字段 schema：

```
run_id | date | ats | company_slug | variant_id | run_no(1-3) |
field_name | expected | actual | pass(Y/N/partial) | screenshot_file | notes
```

**逐字段记录清单（每次测试固定检查这 10 项）：**

1. 姓名
2. 邮箱
3. 电话
4. 城市
5. 最近公司
6. 最近职位头衔
7. 工作经历条数
8. 起止日期
9. 教育背景
10. 技能识别数量

**截图命名规范：** `GH_stripe_V03_run2_skills.png`（ATS_公司_变体_轮次_区块）

## Phase 1 · 测试入口（去哪个网站）

### 通道 A：Greenhouse 候选人端（主通道，零成本）

1. Google 搜索：`site:boards.greenhouse.io software engineer`，或直接访问已知使用 Greenhouse 的公司招聘页（Stripe、Airbnb、HubSpot 等数千家）
2. 任选一个 SWE 职位，点 Apply
3. 上传简历 → 表单**自动填充（Autofill）**各字段 → 这就是解析结果（跑的是 Greenhouse 生产环境解析引擎，不是模拟器）
4. **逐区块截图 → 按 0.3 记录 → 关闭页面。绝不点 Submit**

**选公司规则：** 同一变体的 3 次重复，分别在 **3 家不同公司**的职位上跑——把"公司自定义配置"这个噪音和"引擎本身行为"区分开：

- 3 家结果一致 → 引擎行为（可写入结论）
- 3 家结果不一致 → 配置噪音（记入 notes，不作为引擎结论）

### 通道 B：Lever 候选人端（第二通道，Day 1 需先验证）

1. Google 搜索：`site:jobs.lever.co engineer`
2. **Day 1 第一件事：先手动试一次**，确认 Lever 的申请表是否有客户端解析预览（自动填充）
3. 有 → 照通道 A 流程执行；没有或很弱 → 启用通道 C 替补

### 通道 C：替补——可自助注册的真实 ATS 后台（低成本，真后台视角）

如果 Lever 候选人端拿不到解析预览，用这些**有自助试用、面向 SMB 的真实 ATS** 顶替第二个环境。它们给你完整的 recruiter 后台，视角比通道 A 的候选人端更深：

| ATS | 准入 | 用法 |
|-----|------|------|
| Workable | 15 天免费试用（无需信用卡） | 建一个测试职位 → 用 6 个变体投递 → 后台看解析结果 |
| Recruitee / Manatal / Zoho Recruit | 免费试用或低价月付 | 同上 |

> ⚠️ Greenhouse / Lever **没有**自助试用（销售驱动年费合同，$3,500–70,000+/年）。**不要为拿沙盒走假采购流程**——违反裁判定位的诚实原则。Workday 无公开路径，靠招聘代理合作后补（Cycle 2 议题）。

### 三条红线（合规底线）

1. **真实公司职位页上绝不点 Submit**——上传看预览即走，不产生真实申请，不占用任何公司的招聘资源
2. **不做自动化批量抓取**——全程手动，频率保持人类水平
3. **不伪装采购身份获取沙盒**——裁判卖的是可信度，获取数据的方式本身就是品牌资产的一部分

## Phase 2 · 执行节奏（Day 1–14）

### 测试量计算

```
6 变体 × 2 平台 × 3 次重复 = 36 次上传
每次上传 + 截图 + 记录 ≈ 10-15 分钟
总工作量 ≈ 6-9 小时，拆成 4-6 个低能窗口即可完成
```

### 日程安排

| 时段 | 任务 | 产出 |
|------|------|------|
| **Day 1** | Phase 0 全部 + 通道 B 验证（Lever 是否有 autofill 预览） | 母本 + 6 变体 PDF + 记录表 + 第二通道决策 |
| **Day 2–5** | 通道 A（Greenhouse）：6 变体 × 3 家公司 = 18 次 | Greenhouse 完整数据集 |
| **Day 6–9** | 通道 B 或 C：6 变体 × 3 次 = 18 次 | 第二平台完整数据集 |
| **Day 10–11** | 数据清洗 + 一致率计算 + 异常复测 | pass/fail 矩阵初稿 |
| **Day 12–14** | 缓冲期：补测噪音项、整理截图库、写第一批结论 | 可引用的 5 条发现（喂给 Page A 研究报告页） |

### 一致率计算方式（Kill Criteria 判定）

```
一致率 = 同一变体在同一平台 3 次重复中，10 个字段判定完全相同的比例

判定标准：
≥90%  → 通过技术门，数据可作为产品证据，进入付费报告生产
70-90% → 引擎行为不稳定，需扩大重复次数定位噪音源，延长 7 天
<70%  → 技术门失败，"中立验证层"定位回退，触发 pivot 评估
```

## Phase 3 · 付费页面什么时候做

**结论：Day 1 不做付费页面，做 fake-door。**

| 阶段 | 动作 | 逻辑 |
|------|------|------|
| **Day 1–14** | 只跑测试，不建付费页 | 数据没跑通之前，付费页是空承诺 |
| **Day 14 技术门通过后** | 上线 **fake-door 验证页**：Verified ATS Parse Report 介绍 + $19-39 定价 + "Get my report" 按钮 → 点击进 waitlist 邮箱收集 | 用真实点击验证付费意愿，零开发成本 |
| **首批 waitlist ≥ 阈值** | 手动交付前 10 单（半人工：30-60 分钟/单，$19-39/单，毛利健康） | 首月 10 单的目标不是赚钱，是验证"有人愿意为后台视角付钱" |
| **Day 60 付费门通过后** | 再投入自动化：测试提交和截图采集脚本化，人工只留归因判断 | 归因判断是你判断力的用武之地，其余都是管线 |

### 付费报告的 5 层交付结构（产品定义，供 fake-door 页文案用）

1. **后台真相截图**——简历在真实 ATS 解析引擎里实际被读取的样子
2. **字段级 pass/fail 矩阵**——逐字段 expected vs actual，每个 ATS 一列（不给黑箱总分）
3. **归因 + 修复清单**——哪个具体元素导致失败（双栏/表格/图标/字体/页眉页脚），改成什么
4. **复测验证（半价）**——改完再测，before/after 对照，同时生成 Benchmark 种子数据
5. **排除一个变量**——用证据关闭"格式解析"这个焦虑变量；用户买的不是数据，是确定性

### 营销红线（与测试红线同等级）

**绝不承诺"过 ATS = 拿 offer"。** 解析通过 ≠ 拿到面试；内容质量、匹配度、市场供需都不是这份报告能解决的。

正确表述（防御性承诺）：

> "在你花几百小时优化内容之前，先用 $19 确认机器能读到它。"

排除变量，而不是保证结果——这种克制恰好和裁判定位自洽，且是靠贩卖焦虑做转化的竞品说不出口的话。

## 附：叙事措辞校准（已修正的认知）

Greenhouse 里 recruiter 大概率直接读上传的 PDF 原件，解析字段是辅助元数据（用于搜索和候选人卡片摘要），不是完全替代 PDF 的渲染视图（Workday 才是"解析乱了就是乱码"机制）。

- ❌ 旧叙事："我们截图给你看 recruiter 眼里你的简历长什么样"
- ✅ 修正叙事："解析字段决定你**能否被搜索到、被筛选到**——extraction affects whether recruiters can find and filter you"
