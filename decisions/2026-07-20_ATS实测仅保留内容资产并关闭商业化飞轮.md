# 决策：ATS 实测止于内容资产，不进入商业化与行业基准

> **阶段性结论：四个 ATS 实测产生了有价值的内容发现，但没有产生足以推翻 Gate 1 的商业证据。Flywheel 03 作为独立商业飞轮关闭；已有测试只做一次性内容转化，服务 01（流量与邮件名单）与 04（职场资源资产库）。**

## 执行摘要

- **结论**：ATS 实测不支持作为收费服务（C 端或通用产品）、不支持作为行业基准，Flywheel 03 商业化路线关闭并标记为 `killed`。
- **推翻 V1**：V1 的“收费服务有条件可行、扩样后可升级基准”被本次 Greenhouse 零可观察结果与 Parser/Tenant 双层方差不可聚合推翻。
- **唯一保留项**：把四个 ATS 测试写成 1–2 篇英文 evidence-based 长文，作为 careerradar.io 的 SEO/GEO 内容资产；预算 1–2 天，之后不再追加任何测试。
- **资源回收**：内容发布后归档全部测试工件，注意力回到 01 流量与邮件名单 + 04 职场资源资产库主线。
- **重启条件**：非熟人真实付费、高意向 B2B inbound、可控 ATS sandbox/API、或真实证据相对 heuristic 分数具有显著更高支付意愿。

## 1. 决策背景与证据边界

- 2026-07-17 已启动 ATS 实测，并形成“切换 Workable + Recruitee、建立后台真相叙事”的执行决策。
- 本轮新增 **4 个真实 ATS 申请测试**：Lever、Oracle Taleo、Workday、Greenhouse，使用同一份虚构简历的 DOCX 与文本型 PDF 版本。识别出一组反直觉现象，但这些信息回答的是“ATS 如何表现”，没有回答“谁会为什么结果付多少钱”。
- **V1 报告结论“收费服务有条件可行、扩样后可升级为基准”在本版被推翻**；推翻依据是 Greenhouse 的零可观察结果与 Parser/Tenant 双层方差的结构性不可聚合。
- 前序外部分析因 GitHub private repo 无法读取 `_meta/router.md`，仅基于报告与已有上下文。本决策已重新按本地仓库路由核对。
- 当前仓库未找到“2026-07-17 因 Gate 1 正式否决 Flywheel 03”的独立 decision 文件；因此以本文件作为 2026-07-20 的正式收敛记录，并覆盖 2026-07-17 的继续测试决策。

## 2. 成立的实验结论

1. **页面未展示 ≠ 解析失败**：候选人端可见字段不能直接代表后台 parser 结果。
2. **来源归因必须分层**：账号资料、默认值、地区规则与人工输入会污染对解析结果的判断；Workday Taiwan 案例证明该风险真实存在。
3. **Greenhouse 候选人端可观察产出为零**：在四个 ATS 中，Greenhouse 不向候选人展示任何解析后的结构化字段；姓名/邮箱/电话均需手动填写，无法归因于 parser。因此任何声称能给出“Greenhouse 兼容分”的候选人端工具，其分数不可能来自对该系统真实行为的观察。
4. **不输出虚假确定性**：现有证据不支持“通过率”“兼容性”或结果保证。
5. **8 状态分类表可保留**：它可以成为可引用的方法论框架，但不能被包装成统计基准。

## 3. 核心逻辑审查

### 3.1 Parser 与 Tenant/Config 被错误合并

| 层级 | 主要变量 | 稳定性 | 可泛化性 | 合适的测试方式 |
|---|---|---:|---:|---|
| Parser 层 | 解析引擎、字段抽取、版本行为 | 同版本内相对稳定 | 部分可泛化 | 可控 tenant / demo / sandbox + 固定简历复测 |
| Tenant/Config 层 | 字段展示、必填项、Job Questionnaire、地区规则、申请步骤 | 公司与岗位持续变化 | 不可泛化 | 只能作为案例，不应聚合成 ATS 平均准确率 |

原计划的 `4 × 3 × 2 × 2 × 2 = 96` 次矩阵把两层方差混为一个统计框架。每个 tenant、requisition template 和地区配置都可能形成新组合，矩阵单元不可直接加总；扩样不会自动把案例升级为“正式基准”。

### 3.1.1 候选人端可观察性光谱

四个 ATS 在“候选人能看到多少解析结果”上拉出了完整光谱，这决定了“候选人端解析审计”方法的天花板：

| ATS | 候选人端可观察字段 | 可观察性 | 备注 |
|---|---|---|---|
| Taleo | ~18 项（散落多步骤） | 高 | 但污染最重、人工成本最高 |
| Lever | 7 项 | 中 | 最干净的对照条件 |
| Workday | 3 项 | 低 | 被账号/地区规则覆盖 |
| Greenhouse | 0 项 | 无 | 后台解析完全不可观察 |

因此，**方法产出由目标 ATS 的可观察性决定，而非测试执行质量**。在 Greenhouse 上，该方法产出为零。

如果目标只是测 Parser 层精度，应使用可控环境和固定输入，而不是遍历真实企业申请页面。原设计选择了成本最高、可比性最低的实验方式。

### 3.2 数据不是 Class A，而是高折旧 Class B

- 职位页面生命周期通常以周计。
- ATS 版本、企业字段与地区规则会持续变化。
- “行业基准”需要长期复测，无法通过一次投入永久沉淀。

因此，测试数据更接近**快速折旧的 Class B 资产**。只有将既有发现转化为可长期引用的方法论与 SEO 内容，才可能形成接近 Class A 的复利资产。

### 3.3 C 端单位经济不成立

| 指标 | 当前区间 | 判断 |
|---|---:|---|
| 人工交付成本 | 60–90 min / 单 | 高度 bespoke，无法摊销 |
| 可接受价格 | ¥99–299 | 难覆盖获客、交付、售后与风险成本 |
| 复利属性 | 低 | 每一单都重新产生人工义务 |
| Founder-fit | 差 | **与“情绪依赖型执行”直接冲突，低能量期容易形成履约风险**  |

这不是等待“试点验证”的轻微不确定性，而是结构性不成立，因此不保留 C 端 SKU。

### 3.4 平台与伦理风险被低估

“提交前退出”不能保证无痕。Taleo 测试已创建候选人档案；规模化测试可能污染企业招聘数据、违反 ToS、触发风控或企业投诉。该历史还会削弱未来 B2B 合规可信度。

**测试身份隔离**：本轮测试邮箱使用了 `@careerradar.io` 域名，雇主端可直接将测试申请关联到品牌。若未来出现必须测试的场景，应改用与品牌无关的中性域名。

### 3.5 Gate 1 仍未通过

Jobscan、Resume Worded 等产品已经证明，用户愿意购买的是**低成本、即时、确定性的安心感**。真实证据服务更慢、更贵、结论更保守，而且不能承诺结果。

四次测试改变了**内容价值判断**，没有提供以下任何商业证据：

- 有人持续为真实解析证据付费；
- 真实证据可以卖出覆盖 bespoke 交付成本的价格；
- 真实证据相对 heuristic 评分具有更高付费意愿；
- 交付可以标准化并形成复利。

因此，**新信息不足以推翻 Gate 1**。

## 4. 路径裁决

| 路径 | 决策 | 核心理由 |
|---|---|---|
| C 端收费报告/服务 | **不做** | 单位经济不成立、bespoke 无复利、Founder-fit 差 |
| B2B 企业流程审计 | **不主动做** | 销售周期长、缺少 solo founder 渠道、机会成本过高；仅接受高意向 inbound 再单独评估 |
| ATS 行业基准/准确率项目 | **不做** | Config 层方差不可聚合，数据持续折旧，96 次不产生可信统计量 |
| 方法论 + 案例型内容资产 | **保留** | 可一次性收割已有测试成本，形成差异化 SEO/GEO 内容与可引用框架 |

## 5. 最终决策（一经写入不可修改）

1. **关闭 Flywheel 03 作为独立商业飞轮**，停止 Parse Report、求职季订阅、Benchmark 与 B2B API 的主动产品化；将 `_meta/router.md` 中 03 的状态由 `exploring` 改为 `killed`。
2. **不启动 96 次测试矩阵，不继续扩样，不维护持续更新的 ATS 准确率基准；**Dashboard 中 WK×6、RC×6 变体矩阵直接归档，不再执行。
3. 将已有四个 ATS 实测与 8 状态分类表在 **1–2 天固定预算**内转化为 1–2 篇英文 evidence-based 长文。
4. 在知识库 `decisions/` 补记 flywheel 03 的 kill ADR（否决日期 2026-07-20 + gate 1 理由 + V2 报告作为证据附件）。
5. 内容归入 Flywheel 01 的 SEO/GEO 获客体系，并内链至现有工具、affiliate 页面与 email capture；8 状态表作为 citable framework，而非统计结论。
6. 归档全部测试工件（4 份 Excel、2 份测试简历、截图、报告），不再追加测试；不开发半自动记录工具。
7. 内容发布后结束本轮 ATS 测试，资源回到 **01 流量与邮件名单 + 04 职场资源资产库**主线。

## 6. 内容资产化边界

### 建议角度

- `We Actually Tested 4 ATS With the Same Resume — Here’s What an ATS Score Can’t Tell You`
- `Resume Upload Success Is Not Parse Success: An 8-State Framework for ATS Evidence`
- 可传播的核心发现按锋利度排序：
  1. Greenhouse 向候选人展示的解析证据为零，候选人端“ATS 兼容分”工具在该系统上只能是猜测；
  2. 候选人端可观察性光谱（Taleo 18 项 → Lever 7 项 → Workday 3 项 → Greenhouse 0 项）；
  3. 上传成功 ≠ 解析成功；页面未展示 ≠ 解析失败；
  4. 账号资料与地区规则可覆盖解析结果（Workday 案例）；
  5. 解析结果可散落在多步骤流程中（Taleo 案例）。

### 必须保留的证据纪律

- 明确样本是 **4 个 ATS 实测 case**，不宣称行业代表性。
- 将“上传成功”“页面展示”“后台解析”“账号/地区默认值”分开描述。
- 不发布 ATS 通过率、兼容性排名或结果保证。
- 不把案例数量包装成 benchmark。
- 不为写文章追加新测试；内容只能消化已产生的证据。

## 7. 重新打开 Flywheel 03 的必要条件

仅当出现以下至少一项强证据时，才允许重新评估，而不是因流量、评论或个人兴趣重启：

1. 出现可验证的真实付费：非熟人客户按可覆盖交付成本的价格购买；
2. 出现高意向 B2B inbound，客户自带真实 tenant、明确预算与合规授权；
3. 获得可控 ATS sandbox/API，使测试标准化且边际成本显著下降；
4. 证明真实证据相对 heuristic 分数具有显著更高的支付意愿，而不只是更高的内容关注度。

## 8. 一句话备忘

> **实验记录支持写文章，不支持做生意：收割内容资产后停止追加成本。**
